## 会话共识与顾问默认假定

### 你已明确表达的偏好（拍板）

- **分工**：订阅**只负责节点**（`proxies` / url-test）；[verge/extend/airport-rule-split-extend.yaml](verge/extend/airport-rule-split-extend.yaml) **负责** `dns`、`sniffer`、`geodata`、`proxy-groups`、`rules` 的顶层设计（仓库注释 MECE）。
- **「统一出口」口径（公司已拍板细化）**：**优先**在**同一公司 / 同一业务大类**内保持出口一致（例如别让 **Google** 被自己拆成 CDN 直连 + 搜索走代理两套 IP）。**例外**：像 **微软**，若只有少数子域在国内路径上**不可用或体验极差**（Copilot、部分必应链路等），允许这些子域**单独切到代理出口**（**K）**「大厂 · 💠 微软跨境」），其余微软服务仍沿用 **「大厂 · 🪟 微软」默认直连**——这是「**大厂统一 + 小部分 carve-out**」，与「跨公司必须同 IP」无关；**不要求**微软与谷歌同公网出口。
- **微软直联与 Copilot carve-out**：**大桶** `GEOSITE,microsoft` →「大厂 · 🪟 微软」**默认 DIRECT**；**极少数不能直连的子域**，在 **`GEOSITE,microsoft` 之前**用 **DOMAIN/DAT 补丁**送进 **K）「大厂 · 💠 微软跨境」**（默认 `🌍 节点选择`）；**不靠**整域 `bing.com` 一刀切。
- **GitHub 与微软（当前 [airport-rule-split-extend.yaml](verge/extend/airport-rule-split-extend.yaml) 实际命中）**  
  - **法律/资本关系**：GitHub 属微软；**分流上不按「公司台账」一概而论**，而是按**规则顺序 + geosite 标签**。  
  - **明确走代理优先**：`DOMAIN-SUFFIX,ghcr.io`、`DOMAIN-SUFFIX,npm.pkg.github.com` → **「场景 · 🐙 开发源站」**（列表首项为 **🌍 节点选择**）。  
  - **其余常见于 `microsoft`/`github` geosite 桶的域名**（如 **`github.com` 本站、gist、releases 下载主域等**，以 geosite.dat 归类为准）：命中 **`GEOSITE,microsoft` →「大厂 · 🪟 微软」** → **默认直连**。  
  - **若你希望「整站 github.com 都走代理」**：需在规则中新增 **`GEOSITE,github`** 或对 `github.com` 的 **DOMAIN 规则**指到 **`🌍 节点选择` 基底或「场景 · 🐙 开发源站」**，优先级放在 `GEOSITE,microsoft` 之前——**当前配置未这么做**。
- **局域网**：**开启 allow-lan**—允许其它设备通过 **Mac 的混合/SOCKS 端口**（如 `7890`）走 Verge；**不等于**把手机代理填到 **9090**（见下文 **顾问默认**）。
- **DNS**：**`dns.use-hosts: true`** 已在 [airport-rule-split-extend.yaml](verge/extend/airport-rule-split-extend.yaml) 落实。**继续保持 `ipv6: true`**；不将其理解为「对网站更隐蔽」，而是双栈完整性。
- **广告**：你希望**强效过滤**；在现有 **`GEOSITE,category-ads-all` / `category-public-tracker` → REJECT** 之外，倾向再挂 **`rule-providers` + `RULE-SET`**（见 **F）**），并接受 **reload / 内存** 略增的可选代价。
- **稳定性主张**：主攻 **GEOSITE + DOMAIN 补丁 + 严谨顺序**，**不**为了一致性去整吞机场数万行静态表；超长表的主要代价是 **维护与资源**，误伤主要来自 **DOMAIN-KEYWORD 过粗** 等。
- **`skip-cert-verify`**：你已要求**由我侧先做本机 openssl 摸底**—结果见 **L）**；在 Verge 里对同类节点 **`false` 试错**仍可作最终验收（todo `skip-cert-verify-trial`）。

### 顾问默认、你未反对即视为建议采纳

- **控制面**：`external-controller` **绑定 127.0.0.1**，`secret` **非空**；避免与机场模板一样 `0.0.0.0:9090` + 空密（局域网内被无口令操作内核）。
- **健康检测**：若使用订阅自带 **url-test / 自动选择**，`interval` 放在 **300–600 秒** 量级，避免 **86400s** 级「假自动」。
- **弱节点**：`rc4-md5` 等仅作**备用**；主力用现代传输 + 尽量**校验证书**。
- **合并验证**：每次依赖「扩展 + 订阅」合并时，确认 **最终配置里** `dns` 与 **fake-ip 规则**一致（todo `verify-merge`）。

   「♻️ 自动选择」`interval: 300`，「🔯 故障转移」`interval: 180`（约 [188-242 行](file:///Users/hubery/Library/Application%20Support/io.github.clash-verge-rev.clash-verge-rev/profiles/RZWq9untEa8L.yaml)）；地区组多为 `600`。

## RZWq9untEa8L — 不好的地方与原因

1. **单体超大规则文件**  
   约数万条内联 `DOMAIN-SUFFIX` / 广告域等。  
   **原因**：解析与加载成本高；排错困难；订阅更新常带来大面积 diff，难以审计。

2. **控制面暴露面偏大**  
   `external-controller: '0.0.0.0:9090'`，且 `secret: ''`（约 [24-29 行](file:///Users/hubery/Library/Application%20Support/io.github.clash-verge-rev.clash-verge-rev/profiles/RZWq9untEa8L.yaml)）。  
   **原因**：在局域网或错误端口映射时，REST API 可能被同网段或未授权访问（应改 `127.0.0.1` 并设强 `secret`，除非你有意远程面板且另有访问控制）。

3. **`skip-cert-verify: true` 等_tls 节点参数**（抽样见于 proxies 段）。  
   **原因**：弱化 TLS 校验，存在中间人风险；属于「能连上但安全性打折」的常见机场折中。

4. **混杂弱算法节点**  
   「海外用户专用-*」使用 `rc4-md5` 等（约 [81-83 行](file:///Users/hubery/Library/Application%20Support/io.github.clash-verge-rev.clash-verge-rev/profiles/RZWq9untEa8L.yaml)）。  
   **原因**：已属过时套件，仅适合兼容老环境；不建议作为主力。

5. **配置文件内未包含 `dns:` 段**（全文未检出顶层 `dns:`）。  
   **原因**：DNS 行为依赖 **Verge 全局/合并配置**；若不统一，容易出现「规则以为走了代理、DNS 却走另一路径」的分裂（你当前项目里的 [verge/extend/airport-rule-split-extend.yaml](verge/extend/airport-rule-split-extend.yaml) 是专门对付这一点的）。

## 建议你怎样做（可执行优先级）

1. **策略分工**  
   - **节点与健康检测**：继续用机场订阅提供 `proxies`；若使用「自动选择」，把 `interval` 调到 **300–600 秒** 量级（避免 RCTI 那种 86400）。  
   - **规则**：优先以你维护的扩展（GEOSITE/PROCESS-NAME/VPS IP）为主；**不必**为了「像大机场」而整份吞并数万行规则，除非你确实需要其广告库且能接受加载成本。

2. **安全基线（两条一起改）**  
   - `external-controller` 绑定 **127.0.0.1**（除非你明确要局域网管理）；  
   - `secret` **非空**（与 RZWq 的「全零监听 + 空密」相反）。

3. **DNS 与规则必须同源**  
   若某份订阅不含 `dns`，在 Verge **全局扩展或合并后的配置**中显式补齐 fake-ip / fallback，否则易出现「分流对、解析不对」的隐性 bug（这也是你项目里扩展文件存在的原因之一）。

4. **苹果 / 微软大桶默认直连**

## 答疑与对照本仓库（Extend 双稿：airport / myvps-DO）

### 1）「显式前置 DOMAIN」（计划原文 16–18）是否比我们现在更好？

**不一定更好，是不同套路。** 机场大配置在规则最前面写死 ChatGPT/Claude 等域名；你的 [verge/extend/airport-rule-split-extend.yaml](verge/extend/airport-rule-split-extend.yaml) 同样对境外 AI、Cursor 等用了 **DOMAIN / DOMAIN-SUFFIX**（且还有 **PROCESS-NAME** 针对 Cursor）。差异主要在维护方式：机场再加 **GEOSITE** 兜底或数万条列表；你用 **meta-rules-dat 的 GEOSITE** + 显式域名，**精度与可维护性通常不差于**「只堆 DOMAIN-KEYWORD 的简陋规则」。

### 2）「GEOIP,CN + MATCH」收束（计划原文 18–19）我们现在也是吗？

**是同一类收束。** 你这边是 `GEOSITE,cn` → DIRECT、`GEOIP,cn` → DIRECT、`MATCH` → 「系统 · 🐟 漏网之鱼」，并在此前用 `geolocation-!cn` 等处理「非华语站点」出口。与机场的「国内归 DIRECT、其余走默认组」思想一致。

### 3）Google 静态/CDN 走直连（计划原文 19–23）会不会让 Google 异常？

**多数情况下不会「坏」，但可能带来两类现象：**

- **体验向**：国内直连 `gstatic`/字体/部分 API 往往更快、省代理带宽；**RZWq9** 在规则**末尾**才把这些指到「全球直连」，前面大量 Google 搜索/主站仍可能走代理（与「**同一厂商（Google）内**出口一致」不一致）。
- **一致性向**：若同一会话里**部分**请求直连、**部分**走代理，可能出现 Google 账号/地区信号**不完全一致**（偶发验证码、推荐语言飘移等），**不常见但可能存在**。

你的扩展里 **Google 主桶**是 `GEOSITE,google` 等进「大厂 · 🔍 谷歌」，**没有**照搬 RZWq 那种「末尾一长串 Google 相关子域强制直连」— **满足**「同一厂商（Google）不要被自己拆成双出口」的常见目标。**不要求**微软也必须与 Google 同源出口（你已拍板）。

### 4）`external-controller: 0.0.0.0:9090` + `secret: ''`（计划原文 25–27）是什么意思？

这是 **Mihomo 的 HTTP 控制 API**（换节点、看连接、有时还能改配置），**不是**浏览器上网的 7890 端口。

- **`127.0.0.1:9090`**：只有**本机**进程能访问，相对安全。
- **`0.0.0.0:9090`**：在**所有网卡**上监听——同一 Wi‑Fi 的其它设备若知道你电脑 IP，**理论上可访问该 API**。
- **`secret: ''`**：访问 API **不需要密码**。

所以风险是 **「代理控制面板被局域网或误映射暴露」**，不是「你访问网页会多一跳」的问题。若你只用本机 Verge 面板、不需要手机远程调 API，更稳妥是绑定本机 + 设 `secret`（以 Verge/Mihomo 文档为准）。

### 5）RCTI 的 DNS 分层（计划原文 38–43）值得借鉴吗？我们和他们的差别？

你的扩展里已有 **`default-nameserver` / `nameserver` / `fallback` / `fallback-filter`**，与 RCTI **同一类分层思路**。RCTI 多了 **`use-hosts: true`**、**`ipv6: false`**、另一套 fallback 列表——属于** fine‑tune**，可按你环境试；**谈不上你必须改**才算专业。

### 6）「国内站点大量 DIRECT」（计划原文 43）我们不是这么做的吗？他具体好在哪儿？

**你也在做**：`GEOSITE,cn`、`GEOIP,cn`、腾讯/长视频等显式 DIRECT。RCTI 的「好」不在魔法，在于用**超长静态域名表**把大量国内站提前 DIRECT——**效果与你的 GEOSITE 大桶目标重叠**；维护成本上 **GEOSITE 通常更省事**。他那种列表的优点是：**极老、极偏门的国内域名**有时不在你用的 geosite 标签里，静态表可能补上（代价是规则膨胀）。

### 7）微软整段 DIRECT 的教训（计划原文 47–49）：我们要改吗？有没有未知域名？

**启示**：把 `microsoft.com`、`office365.com` 等**整后缀**标成 DIRECT，等于假设「所有微软子域都适合直连」——在中国网络下省流，但若你需要**始终按海外出口**访问某些国际租户/国际线服务，就可能慢或风控怪。

你当前是 **`GEOSITE,microsoft` 等 →「大厂 · 🪟 微软」且策略组默认已设为 DIRECT**，与 RCTI **同类选择**，不是「你漏了一堆域名」：**GEOSITE 已打包大量子域**；遗漏通常来自 **新域名未入库** 或 **走非典型 CDN**——那时再**补 DOMAIN** 比提前吞全家桶更干净。

**与当前共识对齐**：**不必**为个别不能直连的微软服务把**整桶**微软改为默认代理；用 **K）** 的 **`大厂 · 💠 微软跨境`** 前置 DOMAIN 即可。若国际 M365 全量都要稳定海外出口，再考虑调大桶默认—属**另一档需求**。

### 8）`allow-lan`（计划原文 55）为啥是问题？家里设备互访会误走代理吗？

- **`allow-lan`**：表示**别的设备能否用这台机器当 HTTP/SOCKS 代理入口**（例如手机网关填你电脑 IP + 端口），**不是**「局域网两台 NAS 互传文件会自动经过 Clash」。
- **家里互访**：同一网段直连通信，**默认不经 Mihomo**（除非你把另一台设备的**全局网关**指到运行 Clash 的机器且做了透明代理——那是另一类拓扑）。
- **风险点**：开启 LAN 代理 = **扩大「谁能用你的代理出口」的入口面**；若你不需要给全屋设备开代理，可关；与「家庭文件共享走不走代理」**不是一回事**。

### 9）广告库与「加载成本」（计划原文 64）

- **不是**为了「像大机场」，而是**拦截列表越大，配置越重**。
- **加载成本**：主要指 **Mihomo 启动/热重载配置**时解析规则、构建结构的 **CPU 时间与内存**；**不是**「每条上网请求都重新读一遍 5 万行 YAML 文件」。
- **每次请求**：仍在**已加载的规则集**里匹配，规则越多，平均匹配成本略增；Mihomo 会做优化，但**超大规则**仍可能拉高 CPU（量级因设备而异，**无法在未实测时给百分比**）。
- **可选折中**：大广告库用 **`rule-providers` 外置 + 定期更新**，避免单文件难以版本管理（你若「挺需要广告库」，值得优先考虑这种形态，而不是内联 5 万行当常显正文）。

### 10）「DNS 与规则同源」（计划原文 66–68）：我们现在有隐患吗？

你的扩展 **已包含完整 `dns:`**，若 Verge **合并结果里**最终生效的也是 fake-ip + fallback 这一套，就与「规则按域名分流」一致。

**隐患场景**是：**订阅覆盖/未合并扩展**导致运行时 **DNS 仍是全局直连** 而规则假定 fake-ip——会出现「看起来该代理的域名解析却不对」的疑难。这不是你 YAML 写错，而是 **Verge 里合并顺序与是否勾选扩展** 要**核对一次**（对应 todo `verify-merge`）。属**提醒**，不是已认定你现状有问题。

### 11）微软服务有时需要代理？具体场景（计划原文 68–69）

**有，但不人人遇到。**

- **国际 Microsoft 365 / Outlook.com**：若直连解析到**国内/近邻优化路径**，有时与**租户所在区域**或**合规检测**预期不一致；走稳定海外出口可能更「像在海外办公」。
- **Azure 门户、部分 `*.azure.com` 资源**：偶尔直连**慢**或 CDN **命中差**，走代理可试一下。
- **Copilot / Bing / 部分新服务**：你已选择独立代理分组路径 **K）**；**不**默认为「整桶微软改代理」。

**与当前 YAML 对齐**：`**GEOSITE,microsoft` →「大厂 · 🪟 微软」默认直连**仍为基底；单列服务异常时用 **前置 DOMAIN + 💠 组**或**手动切组**扩容，按需迭代。

### 12）「机场专用弱节点 / skip-cert-verify」（计划原文 69）是什么意思？

- **弱节点**：如 **rc4-md5** 等**陈旧加密**，易被审查识别或不满足你对「只信现代密码套件」的要求——**仅建议作备援**。
- **`skip-cert-verify: true`**：连接节点时**不校验 TLS 证书**（或宽松校验），中间人更容易伪装成节点——**在不可信 Wi‑Fi 上风险更大**；机场为降低证书部署成本常用，**你若在意安全应优先用可正常校验证书的节点**。

### B）局域网代理 vs 9090 控制口（把话说死）

- **「局域网设备用 Mac 上的 Verge 上网」**靠的是 **`allow-lan: true` + 代理端口**（如 HTTP 混合端口 `7890`，以你 Verge/Mihomo 实际为准）。手机/其它电脑把**系统或应用的代理**设为 `Mac 的局域网 IP:7890`，流量才进 Mihomo 再出站。
- **`external-controller`（常见 9090）**是 **Mihomo 的 REST 管理 API**，用来被 **yacd/Verge 面板/脚本** 读写策略、看连接；**不是**「填在 Wi-Fi 代理里」的那个地址。把 9090 绑 `0.0.0.0` 且 `secret` 为空，等于放行他人在局域网**无口令操作内核**，与你会不会开局域网「上网代理」是两件事。

你这边的明确偏好：**保留 allow-lan**（局域网走 Mac 代理）— 没问题；仍建议 **9090 绑 127.0.0.1 + secret 非空**。

### C）DNS `use-hosts` / `ipv6`「配不配」的可感知差异（举例）

- **`dns.use-hosts: true`**：解析时叠加 **`/etc/hosts`**。例：你为内网 NAS 写了 `192.168.1.50  nas.home`，Chrome 走路由 Mihomo DNS 时也按这条走，**内网名归因更稳**。不配也未必错。
- **`ipv6: false` vs `true`**：对你当前 **`ipv6: true`**，`false` 更偏只管 IPv4 解析链；在**纯 IPv6 或强双栈站点**上，两种设置下**偶发的解析/连接路径**可能不一致。不是要你必须改 RCTI；只是回答「改掉会有什么现象」。

### D）稳定性 vs 规则「膨胀」（把代价说清楚）

你要的「该直连不走代理、该代理不回落直连」，取决于 **顺序、标签与补丁**，不靠「条目必须上万」才有。

**膨胀的代价**：配置 **reload 更慢、常驻内存更大、列表人肉难审计、订阅大包 diff**。主要不是「每次上网重读磁盘 YAML」——规则加载进内存后有内部结构。**误分流**的更常见诱因是 **`DOMAIN-KEYWORD` 过粗、顺序错了**，而不是「多到一定条数就必然不稳」。

### E）Bing / Copilot 走哪条策略、和「微软直连」怎么并存

- 规则上 **`GEOSITE,microsoft` →「大厂 · 🪟 微软」**；该组**默认 DIRECT**，故 **多数微软域**先尝试**家宽出站**。

- 命令等价于：`openssl s_client -connect <入口主机>:3026 -servername tw1.ninjanode.pro -verify_hostname tw1.ninjanode.pro`
- **结果**：`Verification: OK`，`Verified peername: tw1.ninjanode.pro`，`Peer certificate` 的 CN 与 SNI 一致，TLS 1.3 握手成功。

**含义**：在 **标准 TLS + 当前本机 DNS 解析链** 下，该入口呈现的服务器证书**可通过** openssl 校验；**强烈暗示**可把 Mihomo 里对应 outbound 的 `skip-cert-verify` 改为 **`false` 试错**。**最终仍必须以 Verge/Mihomo 内实际连接日志为准**——AnyTLS/客户端指纹等与裸 `openssl` 路径不尽相同，若在应用内报错再回退 `true` 即可。

用户在 Verge 内的操作（单节点改过、reload、看多一段日志）仍可作为复核步骤，但不是「只能从 GUI 起手」的必要条件。
