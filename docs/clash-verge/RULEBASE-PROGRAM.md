# 自用规则库（Rulebase）—— 项目背景与长期目标

<!-- 描述性语言以中文为主；配置键、客户端名、专有名词保留原文。 -->

## 1. 我们在做什么

维护一份**长期迭代、与具体机场解耦**的用户侧规则与分流体系：借鉴社区与优质订阅中的**物料与分组经验**，收敛成**符合自家使用场景**的「语义 / 目的 ⇄ 策略组」设计，并在此基础上沉淀**可直接使用**的配置（或从统一 **base** 生成的各端产物）。

**近期落点：** 以 **Clash Verge + Mihomo（Extend 覆盖）** 为主；**演进目标：** 同一套理念与出站/分流意图，适配多终端、多语法，使家人在任意设备上获得**一致体验**（同类业务如 TT / Google / 境外 AI 等走相同分组与同类出口策略）。

## 2. 订阅与「谁拥有代理组 / 分流」

**既定取向（与你当前口径对齐）：**

- **从机场订阅中取用的主要是节点信息（`proxies` / 等价结构）**：用于填充 `proxy-groups` 中的 leaf 或可拨号成员。
- **代理组拓扑、分流规则（`rules`）、DNS/sniffer/geodata 等策略层**优先由 **我们自有模板（Extend / base）维护**，不因换机场而放弃这套结构。

据此，前文若出现「套用机场自带 `proxy-groups` + 自有规则」的讨论，与你的模式**不一致**；你的模式是：**节点来自订阅更新，分组与分流来自自有规则库**，仅在合并实现上要**防止**订阅全文刷新时把我们的顶层键洗掉（见下文「隐患」）。

## 3. 「语义 / 目的」与「策略组」

在你当前设计假设下：**每个稳定的语义桶对应一个独立的策略组**（甚至命名上也能对齐，如 TT、Google、境外 AI、`🛑` / `🍃` 等）。在此前提下：

- **与「社区按语义拆规则集」的共性：** 都是对「这一类流量归哪一档策略」建模。
- **此前区分时的侧重点：** 社区公开集通常**不出现**你家面板里的 Emoji 组名；且同一条域名在不同人 profile 里可能进不同组。你们若把「组名 = 语义」固化为私有规范，两套叙事在工程上即可**收敛**，差异主要在**是否与机场自带组名同构**，而不是是否与「意图」对立。

### 重叠与顺序

若有**两套规则都可能命中同一流量**且落到**不同策略组**：**只有更靠上的一条生效**。若你希望「广告先于媒体」，则广告规则应整体上位于媒体规则之前——这与「域名既可能被标为广告又可被归为媒体站点」并不矛盾：工程上由**你方规则表中的顺序**裁定，产品上可以解释为「默认当广告拦，除非前面另有更具体放行」等。

## 4. 换机场时「稳 / 不稳」指什么

在**坚持自有分组 + 自有分流**的前提下：

- **稳定的部分：** 规则库按组拆分、主编排里的 `RULE-SET` 链、语义与组名映射——**不必**因换机场而推翻哲学；只需保证新拉取的**节点名称**仍能被你的 `proxy-groups` 正确引用（或你在模板里对名称做了稳定别名/筛选）。
- **需要检查的部分：** 新订阅若带来**同名不同义**的 `proxies`、或节点命名规则大变，你的 `proxy-groups` 里 `proxies` 列表是否仍合法；以及 Verge 合并时**订阅是否覆盖**了你的 `rules` / `proxy-groups`（策略层是否仍来自 Extend）。

**「重新导出按组拆的规则文件」**仅指：若你**某次**仍从「机场提供的整包 snapshot」里抽规则做分析，换一份 snapshot 自然要**重跑脚本**；若日常只维护**自家 base**，则**不是**每次换机场都要重做规则库，除非你要吸收新机场规则物料做 diff。

## 5. 只用订阅节点、不用机场自带分组与分流时的隐患（简要）

| 风险 | 说明 |
|------|------|
| 合并覆盖 | 若客户端把「订阅」当成**完整 profile** 合并，刷新后可能**覆盖**你的 `rules` / `proxy-groups`。应用靠 **Extend 优先级** 或等价机制，确保**策略层来自你方**。 |
| 节点命名漂移 | 节点 `name` 若随订阅更新变化，引用它们的 `proxy-groups` 需同步或使用稳定选择逻辑（如 `include-all` + 过滤，视客户端能力而定）。 |
| 机场侧假设 | 少数订阅与面板功能绑定特定组名或内置规则；**你不采用**时一般无妨，仅当使用面板「一键功能」时可能失效。 |
| 重复与数量 | `include-all` 类写法会带入全部节点，组内列表过长时影响可读性，可在模板侧过滤或用手工白名单。 |

以上不是反对「只用节点」；而是实现上要**显式处理**合并顺序与节点引用。

## 6. 模块化与顺序（组内是否「无所谓」）

- **组与组之间**的大块顺序：必须保持你们设计的**优先级**（如补丁域、广告、业务组、GEOIP、`MATCH`）。
- **同一策略组对应的多份子文件（如方案 B）：** 拼接后的**整体顺序**须与原列表一致。
- **同一组内**若规则**互斥**（不同 `DOMAIN` 永不重叠），调序常不改变结果；若存在**可重叠**的匹配（如 `DOMAIN-KEYWORD` 与 `DOMAIN-SUFFIX` 同时可能命中同一主机），**组内顺序仍可能影响结果**。故「组内完全无所谓」**不成立**，除非已证明无重叠或已接受重排风险。

## 7. 方案 C、RULE-SET 与「映射到组」

- 在 Mihomo 常见用法中，**`RULE-SET,provider_name,策略组名`** 为整段 payload 指定**统一出口组**；即：**许多拆法下「去哪个组」写在主编排这一行**，而不是每个子文件各行尾再写组名（classical 也可采用带策略列的扩展写法，视具体格式与版本而定——实现时以 Mihomo 文档为准）。
- **「先按公司 / 业务维护表，再映射到组」：** 指在 **base** 层用「业务桶」（如 Google 系、Netflix、邮件）维护域名/规则物料；**生成期**再生成带你们**策略组**列的规则或带统一策略的 `RULE-SET` 片段。若**同一业务桶**内需多种出口，则需在 base 中**再分子桶**或拆成多个 `RULE-SET` 并在主编排中按顺序引用。

方案 C 与「按策略组拆分」可在不同**抽象层**并存：C 偏**物料与知识库**组织，A/B 偏**落盘为 Mihomo 时的文件切片**。

## 8. 多终端一致体验（路线图）

**目标状态：** 维护一份与客户端无关的 **base**（规则意图、组名约定、业务分类、顺序与注释），再 **派生**：

| 方向 | 说明 |
|------|------|
| **第 1 阶段（当前优先）** | **Clash Verge + Mihomo**：**`verge/template/*-rule-split-extend.yaml`** 为协作主稿，`render-local.sh` 出本机粘贴稿；`rule-providers` / `RULE-SET` 按 **`# >>> rulebase:*` 分段**维护；**`verge/analysis/`** 承接忍者云等**离线拆解与反哺**（脱敏见 §13）。 |
| 第 2 阶段（iOS 侧） | **Quantumult X、LOON、Shadowrocket**：各端模板 / 片段由同一 **base** 派生，与 Verge **同一分组哲学与出站意图**。 |
| 第 3 阶段（OpenWrt 侧） | **OpenClash、Passwall、Passwall2、luci-app-xray** 等：规则或订阅转换模板注入，与 base 对齐。 |
| 其它 | **Sing-box** 等按需接入同一 base，不阻塞前两阶段。 |

**一致性的含义：** 同一业务标签（如 TT、Google、境外 AI）在各端**策略意图一致**；**出口 IP 是否完全一致**还受各端落地实现、节点健康度、DNS 与 sniffer 差异影响，需在验证 playbook 中抽样对齐（可与 `hjs-egress-ip` 等探测联动）。

## 9. 与本仓库其它目录的关系

- **`verge/derive/parts/`**：**机场主线**的策略与 **Verge/Mihomo 运行时壳** 分层真值源；合并为 **`verge/template/airport-rule-split-extend.yaml`**（见 **`verge/derive/README.md`**）。  
- **`verge/template/*-rule-split-extend.yaml`**：**可提交的**策略层成稿（主线为合并产物；个人稿不经 `parts/`）；进库须遵守 **§13**。  
- **`verge/analysis/airport-a/`**：对**机场A订阅快照**的整理、去重、片段化与审计；结论用于反哺 **Extend** 与各 modular 片段，**不等于**最终唯一真值源；**含敏感信息的快照与节点分析不得提交**（见 **§13**）。  
- **`verge/analysis/airport-b/`**：对**机场B订阅快照**的离线分析与模块化拆分，结构与 airport-a 保持一致，便于对比不同机场的规则物料。

## 12. 执行口径（已定稿）

### 12.1 阶段边界

**先**把 **Verge** 链路做扎实（**`verge/analysis` 反哺 → `verge/derive/parts` → `compose` → `extend` 主稿** + `render-local.sh` + 可选校验）；再依次做 **Quantumult X、LOON、Shadowrocket**，然后 **OpenClash、Passwall、Passwall2、luci-app-xray**（顺序见 **§8** 表）。

### 12.2 规则真值源

- **手写与协作主源（Verge / Mihomo 第一阶段）：** **`verge/derive/parts/`** + **`verge/template/*-rule-split-extend.yaml`** —— 其中 **机场主线**为 **`10-runtime-verge-mihomo.yaml`**（客户端运行时壳）与 **`20-routing-mihomo.yaml`**（`proxy-groups` / `rule-providers` / `rules`），由 **`verge/scripts/derive/compose.sh`** 合并为 **`template/airport-rule-split-extend.yaml`** 后，再走 **`render-local.sh`** 生成本机粘贴稿。**Quantumult X / LOON / Shadowrocket** 等：未来应以 **与 `20-routing-mihomo.yaml` 相同的策略语义** 为输入做语法派生（本仓库尚未落地转换器）。  
- **与「忍者云」过长整包的关系：** 订阅全文仅作 **一次性或周期性分析输入**；落盘到仓库的应是 **结论**（策略语义、组名、`RULE-SET` 编排），而非复制整份远程配置。  
- 脱敏红线与协作口径见本文 **§13**。

### 12.3 模块化产物是否进 Git

- **脱敏后的**规则片段、`rule-providers` 配置、主编排骨架、**`proxy-groups` 名与分流规则语义**——**允许并鼓励进 Git**，便于 diff、给家人/协作者「只拿规则与分组哲学」。  
- **禁止**入库内容见 **§13**（含**具体机场名称**相关的**带 token 订阅、节点密钥、可追溯个人身份的节点清单与分析**）。

### 12.4 大组二次切块（维护者采纳的工程默认值）

转发路径上，命中性能主要由 **内核建好的匹配结构 + 命中顺序** 决定，与「磁盘上是 1 个还是 8 个 classical 文件」**几乎无关**；差异主要在 **进程启动时的解析与 I-O** 与 **日常维护、git diff**。故切块以 **启动与可维护性** 平衡为主，不靠「越多越好」去追求转发提速。

建议默认值（脚本可做成配置项）：

| 维度 | 建议 | 理由 |
|------|------|------|
| **默认** | **每策略组 1 个** `RULE-SET`（单 classical 文件） | 分段最少；与「按策略组模块化」心智一致；社区常见「一意图一 provider」也多在 **数千～一万级** 规则量级，单片可接受则不再切。 |
| **触发二次切块** | 单组 **≥ 8000 条规则行**，或粗略 **≥ ~600KB 纯文本**，二者 **任一** 达标即切 | 低于此规模再拆，对启动收益的边际极小，却增加编排长度与失手乱序的概率；阈值与常见「单文件仍可 diff」的 Git 实践接近。 |
| **切法** | 在 **不改变全局命中顺序** 的前提下，按连续段优先 **hostname 类 vs `IP-CIDR(6)` vs `PROCESS-*`**；若单类仍超限，再按 **固定行数切块**（如每块 **4000～6000 行**，边界勿打乱相对顺序）。 | 便于人工审阅与 blame；避免为拆而拆出过碎文件。 |
| **同组 `RULE-SET` 条目数上限** | 建议 **≤ 10～12 条**/组；超限则优先 **抬高单块行数阈值** 或与维护者会商，而非无限拆片 | **过多 provider** 会线性增加载入与配置噪音；与一般「单层十几个规则集以内」的工程习惯相容。 |

若在实际设备上测得冷启动明显增加，可把阈值略调高（更少文件）或减少同组条目数目标的激进拆法。**数据面体验**仍以 **规则语义与顺序正确** 为第一优先。

### 12.5 验证与 CI

- **开发与自测阶段：** 对生成产物做 **尽可能完整** 的校验——例如：YAML 语法、必选键、`proxy-groups` 名引用存在性、可选「与快照规则条数或逐行 hash」对比、`verify_phase04_concat` 类推的拼接等价性、`render-local.sh` / 小型集成测。  
- **长期维护：** CI 以 **轻量闸门** 为主：**语法与 schema 级校验**、可选 **golden 规则条数或校验和档** 防手滑大规模误删、关键生成器的 **单元测试**；**不必**在每次 PR 上跑全量重对比（除非变更触及生成器核心）。

## 13. 可进库与脱敏红线（必须遵守）

以下适用于 **任何** 拟提交到本公开仓库的路径（含 `verge/template/`、`refactor-p04-rule-providers/`、`verge/analysis/**` 下**故意**提交的说明性文件等）：

**禁止出现（含链接查询串、Base64、拼在 URL 里的 token）：**

- 机场 / 面板 **订阅完整 URL**、**订阅 token**、**UUID / 密码 / 证书私钥** 等节点鉴权信息。  
- **完整可拨号节点列表**（含 server、port、password、uuid 等），或能 **唯一还原** 你个人订阅的一对一节点导出。  
- **具体机场名称**（及同类）带 **可识别你账号** 的节点信息、订单或面板导出；与「仅含策略组名 + 规则匹配行、无上述字段」的材料区分对待。

**允许作为「可分享 base」内容：**

- **`proxy-groups` 名称、类型、结构**（不含真实节点敏感字段；节点仍由各人本地订阅提供）。  
- **分流规则**：`DOMAIN` / `GEOSITE` / `RULE-SET` / `GEOIP` / `MATCH` 等 **策略语义**（脱敏后）。  
- **公开** `rule-providers` URL（如社区 ruleset）、**无密钥** 的 geodata 配置说明。

**流程上：** 提交前对「从机场快照回溯」的素材做 **strip**；CI 或本地脚本宜增加 **敏感键扫描**（`password` / `uuid` / 订阅 URL 模式等）作提醒。
